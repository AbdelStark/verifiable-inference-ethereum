# Engineering Roadmap (`M0` to `M4`)

These rows match the repository's GitHub milestones, which hold the full scope and configuration.

| Milestone | Scope | Exit gate |
|---|---|---|
| **M0: Verified foundation** | Everything in the tree builds and passes in CI on pinned toolchains and agrees with `SPEC.md`. Speculative and unproducible code is gone. `publicDigest` commits to the tokens in place of the on-chain Fiat-Shamir replay. | CI is green on `main` with Rust 1.99.1, Foundry v1.8.6, solc 0.8.38 and `evm_version = "osaka"`; format, lint and lockfile gates run in CI and `make check`; no native Circle STARK or `SASHBIN1` code remains and M5 is marked not planned; the Solidity fixture is generated from Rust with drift detection; `publicDigest` binds the tokens; `SPEC.md` and the code agree; every negative control passes in the suites `SPEC.md` lists; the docs separate what exists from what is planned. |
| **M1: Measured local settlement on Anvil** | Mine the TinyLlama settlement on a running anvil node, and measure it. Pin `code_size_limit = 24576`, `gas_limit = 16777216` and `isolate = true` (after splitting the test contract, which is over the limit). Gate gas with committed snapshots, regenerated by `make check` and CI, and an `assertLe` budget per snapshot. Take authoritative gas from receipts on `anvil --hardfork osaka --enable-tx-gas-limit`, labelled with the hardfork and Foundry version, and publish `--gas-report` as a CI artifact. Amsterdam figures are provisional and outside the exit gate: `docs/EVM-GAS-MODEL.md` §4 records them from a Foundry nightly, and #24 re-measures them on a stable release. The docs replace their estimates with these measurements. | Dev-mode settlement is mined on local anvil under Osaka; `SashGridVerifier.verifyGrid` on the 23-segment run costs under 350k gas; every contract, test contracts included, stays under 24,576 B. |
| **M2: Real SASH proofs through an SP1 guest** | Run a verifier-only extraction of SASH's `verify_composed` over its vendored `nitroo` Stwo in an SP1 v6 `riscv64im` guest, one per segment. The guest rejects unsound parameters, lax or skipped gadgets, and token ids `>= P`, checks the token bindings, and commits its segment claim with `sha256(tokIn)` on `B0L0` and `sha256(tokOut)` on `head` (`SPEC.md` §1). M2 also decides where the `Fixed.params` hash is pinned. | All 23 segments verify in the SP1 executor with cycles, peak memory and the BLAKE2s share recorded; tampered and unsound bundles and token ids `>= P` are rejected; the fixture regenerated from the bundles is byte-identical to the committed one; the go/no-go for M3 is recorded here. |
| **M3: Compressed SP1 settlement on Anvil** | One aggregator guest verifies the 23 SP1 compressed segment proofs and commits exactly the 32-byte `publicDigest`. Settle through `Sp1SashSegmentVerifier` against the real SP1 verifier on anvil, with `allowDevVerifier = false`. Decide at M3 start the wrap (Groth16 or PLONK) and the binding (a pinned verifier or the `SP1VerifierGateway`). | Aggregated settlement costs under 600k gas on Osaka, measured from a receipt on `anvil --hardfork osaka --enable-tx-gas-limit`; the Amsterdam figure is recorded; no dev mocks are on the settlement path. |
| **M4: Public testnet settlement on Hoodi** | Deploy with `allowDevVerifier = false` to Hoodi (`560048`); Sepolia (`11155111`) is optional. Fork tests assert the deployed SP1 verifier's `VERIFIER_HASH` and `VERSION`; `SECURITY.md` gains a pre-deployment audit checklist, including Slither. Enroll the TinyLlama manifest and submit a live verification transaction. | A finalized Hoodi transaction settles the TinyLlama run and emits `InferenceVerified` with a non-dev `VerifierKind`, with `tx.gasLimit <= 16,777,216`; the gas breakdown reproduces the receipt's `gasUsed` as `max(standard + execution, floor)`; the fork id, addresses and transaction hash are recorded. |

Native Stwo-in-Stwo recursion (M5) is not planned. It is reopened only if SASH proofs become consumable by StarkWare's circuit recursion, StarkWare publishes a Solidity S-two verifier, or a measured design fits `EIP-7825` (or a multi-transaction fact-registry design is accepted).
