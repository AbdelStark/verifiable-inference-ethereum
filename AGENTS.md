## 1. Mission and technical scope

`verifiable-inference-ethereum` implements an Ethereum EVM and Solidity verification stack for **SASH verifiable LLM inference** (`sg-ai-safety-hub/zk-inference-prover` pinned at `eb95bfa887299d1637550228d42086c27cbb2b3b`, built on `NitrooZK-stwo` / Stwo Circle STARKs), progressing from local Foundry unit and Anvil dev-mode verification to the public **Hoodi** testnet (`560048`, the exit-gate chain), with **Sepolia** (`11155111`) optional.

Reference LLM target: `TinyLlama/TinyLlama-1.1B-Chat-v1.0` (`fe8a4ea1ffedaf415f4da2f062534de366a451e6`), SASH profile `y-attnout-w12`, `S = 32` tokens (`25` prompt tokens + `8` generated answer tokens ending in EOS `2`, split across `23` segments: `B0L0..B0L21` + `head`).

## 2. Non-negotiable engineering invariants

1. **No overclaiming.** An accepted verification proves **quantized execution integrity** for one declared run of an enrolled `(preRoot, modelRoot, fixedHash)` manifest under SASH's `y-attnout-w12` relation. Never claim output safety, alignment, floating-point equivalence, or zero-knowledge hiding (SASH inner proofs use `LOG_BLOWUP = 1` without trace blinding, and public settlement opens prompt/response tokens).
2. **Explicit cryptographic assumption tracking.** Raw SASH segment proofs rely on `BLAKE2s` Circle STARK + GKR (~100 conjectured security bits, post-quantum candidate). Compressing 23 wide segments through the SP1 v6 BN254 PLONK wrap (sp1-sdk `6.10.0`, circuit `v6.1.0`), verified on-chain by the pinned, ownerless `SP1VerifierPlonk` v6.1.0 (`VERIFIER_HASH` `0x5a093a2fcb46394f5cadfe55c44d4d572fad9cec7aeb38026b0278322ef07fac`; `SECURITY.md` §6), shifts the outer assumption to classical BN254 pairing soundness, the Aztec Ignition universal SRS (176 participants, one honest suffices) and SP1 v6 circuit soundness. Keep `VerifierKind` explicit in every contract, event, and receipt.
   - Not Groth16: its v6.1.0 phase-2 setup is circuit-specific, with 18 participants and no public call.
   - Not the `SP1VerifierGateway`: its owner can route any verifier.
3. **Hard separation of dev-mode mocks.** `DevTranscriptSegmentVerifier` is strictly restricted to `block.chainid == 31337` (Foundry / Anvil) AND blocked whenever `VerifiableInferenceSettlement.allowDevVerifier == false`. Never weaken either guard.
4. **Bit-exact cross-language parity.** Rust (`crates/sash-evm-primitives`) and Solidity (`contracts/src/`) must agree bit-for-bit on the grid checks and on the sha256 `manifestRootsHash`, token hashes and `publicDigest` byte layouts (`SPEC.md` §1.3). Any change to Rust primitives must regenerate `contracts/src/sash/TinyLlamaFixture.sol` (`make vectors`, generated from `tinyllama_fixture.rs`; never hand-edit it) and verify it (`make check`).
5. **EVM consensus discipline.** Osaka (mainnet, Hoodi) binds:
   - every settlement transaction stays safely below the `EIP-7825` cap of `16,777,216` gas;
   - it accounts for the `EIP-7623` calldata floor, where gas is `max(standard + execution, floor)` and the floor is `10` / `40` gas per zero / non-zero byte;
   - every contract fits `EIP-170`'s `24,576` bytes.

   Amsterdam (live on Sepolia, provisional until mainnet activation) is measured alongside:
   - the cap counts execution gas only (`EIP-8037`);
   - the floor is `64` gas per byte (`EIP-7976`);
   - `24,576` bytes stays the project's code size limit, although Amsterdam allows `65,536` (`EIP-7954`).
6. **Outward actions require explicit human approval.** Never run `git push`, open PRs/issues, broadcast transactions to public RPCs/testnets, invoke hosted prover networks, download multi-GB weights, or spend paid compute without explicit approval in the active session. A request to work issue #N is that approval for pushing its `issue-N-*` branch and opening its PR (§6), and for nothing else.
7. **Zero secrets or personal data.** Never commit private keys, RPC URLs with API keys, `.env` files, or large binary proof archives (`runs/`, `*.tar.gz`, `*.safetensors`).

## 3. Engineering principles

User-decided rules with the same bar as the invariants.

- **Do not preserve backward compatibility.** Remove obsolete paths instead of adding compatibility layers, fallbacks or migrations.
- **Choose the simplest implementation that fully meets the current requirements.** No speculative abstractions, configuration or indirection.
- **Grow the system in layers**: smallest end-to-end version first, each capability on top of a stack that already works (the `docs/ROADMAP.md` milestones are those layers). Never trade a working stack for unfinished complexity.
- **Keep components modular and concerns clearly separated.**
- **Prefer established, well-maintained libraries**; lean on the dependencies already in the workspace before writing your own or adding crates. Check a library's docs/types before assuming it lacks a capability.
- **Make architectural decisions for the long term.** No stopgaps meant to be replaced later.

## 5. Testing and verification

Before declaring any change complete, run:

```bash
make check
```

`make check` enforces `cargo fmt`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, `cargo test --locked --workspace` (including the real TinyLlama-1.1B 23-segment grid, its digests pinned to `SPEC.md` §1.4, and the Rust rows of the `SPEC.md` §2.1 negative-control table; settlement-level controls run in Foundry only), byte-exact sync of the generated `contracts/src/sash/TinyLlamaFixture.sol` with the Rust export (`export_vectors` run `--locked`), and, whenever Foundry is installed in `PATH`, `forge fmt --check`, `forge build --locked --sizes` (fails if a submodule differs from `contracts/foundry.lock`), `forge lint --deny warnings`, `forge test` (with `contracts/snapshots/` deleted first) and a check that the regenerated gas snapshots match the index, then `make anvil-demo`; whenever `cargo-prove` is installed, `make sp1-check`; and, on an x86_64 host where the SP1 `v6.10.0` image pinned by digest in `sp1/scripts/docker-guests.sh` is also present locally (it is never pulled), `make sp1-docker`, which fails unless the Docker-built segment and aggregator guests match the committed `sp1/{segment,aggregator}-guest.elf.sha256` and `sp1/{segment,aggregator}-guest.vkey`; then, when `cargo-prove`, those two ELFs and the TinyLlama bundles in `BUNDLES` (default `runs/tinyllama`, `make bundles-download`) are all present, the `sp1-bundles` CI job's main path: `make sp1-execute` on all 23 segments into a temporary `OUT`, then `make sp1-fixture-check`; and, when `cargo-prove`, those two ELFs and the TinyLlama proofs in `PROOFS` (default `runs/tinyllama-proofs`, `make proofs-download`) are all present, `make sp1-proofs-check`. sp1-build runs the image as `linux/amd64`, and its emulated build hangs on arm64 hosts.

`make check` runs locally and caches nothing. CI runs the same gates (§8), and on a PR only the jobs the change reaches: `sash`, `sp1-workspace`, the executor suite (`sp1-cached` or `sp1`) and `sp1-bundles` run when it touches `sp1/`, `crates/sash-evm-primitives/`, `contracts/fixtures/`, the root `Cargo.toml` or `rust-toolchain.toml`, `Makefile` or `ci.yml`, and are reported as skipped otherwise. On a PR the `sash` job restores the synthetic corpus and the built oracle from the cache keyed by `sp1/scripts/corpus-key.sh` (a hash of every file they are built from, listed there) and checks them without rebuilding upstream SASH, while `sp1-cached` runs the executor suite on the cached corpus without waiting for `sash`; a change to any of those files misses the cache, runs `sash` in full and `sp1` on its artifact. Pushes to `main`, the weekly scheduled run and a manual run never restore it: they run everything in full and save the cache for PRs. `sp1-bundles` runs the Docker-built segment guest from the same run's `sp1-workspace` on the TinyLlama bundles, downloaded from their public Hugging Face dataset (`sp1/scripts/tinyllama-bundles.sh`, anonymous, cached by the hash of `sp1/pins/tinyllama.sha256`): on a PR, `sp1/scripts/sp1-execute.sh` on `B0L0`, `B0L10` and `head` and the real-bundle controls, which use only those three; on pushes to `main`, the schedule and a manual run, `sp1-execute.sh` on all 23 and `sp1/scripts/sp1-fixture-check.sh`; and on every event `sp1/scripts/sp1-proofs-check.sh` over the 23 published segment proofs (`sp1/scripts/tinyllama-proofs.sh`, anonymous, cached by the hash of `sp1/pins/tinyllama.proofs.sha256`). Neither `make check` nor `sp1-bundles` runs two segment executions at once: the native executor keeps guest memory in `/dev/shm`.

- **Gas snapshots are committed** in `contracts/snapshots/`. An intended gas change fails `make check` until the regenerated snapshots are staged; give the cause in the PR. A Foundry or solc bump also changes them; name the bump as the cause. Keep the measured figures in `docs/EVM-GAS-MODEL.md` §4 and §5 equal to the snapshots and to the table `make anvil-demo` prints; its deployment and `enrollModel` rows aren't gated, so check them whenever a contract changes. A test's `assertLe` budget is raised only for an intended change, with the reason in the PR.
- **A change that moves `sp1/segment-guest.*` or `sp1/aggregator-guest.*` must re-prove.** CI fails until `sp1/pins/tinyllama.proofs.sha256` and `contracts/fixtures/tinyllama.plonk.json` match the new guests: `sp1-proofs-check.sh` verifies the published segment proofs against the pinned segment vk and `SEGMENT_VKEY` and requires the published PLONK proof to render to the fixture under the aggregator's pinned vkey (`sp1-host plonk-fixture`), and the `plonk_fixture` test requires that vkey in the fixture. Re-proving is paid GPU work and needs approval (§2.6).
- **Write tests when a change touches the protocol**: grid checks and settlement guards. Assert against `SPEC.md` and the primary-source vectors, not against the implementation.
- **Don't add tests for docs, cosmetic changes, trivial wiring or config.**
- **A failing invariant test is a real regression: fix the code, never weaken the test.** Never regenerate the fixture (`make vectors`) or edit a primary-source vector to make a failing test pass; the fixture changes only with an intended Rust primitive change (§2.4).
- **A grid-level negative control lands in both suites**, Rust and Foundry, never on one side only. Settlement-level controls (token binding, proof bytes, verifier gating, replay) run in Foundry only. A guest-level control runs natively and in the SP1 executor, never on one side only, except a control that no bundle can reach (G8, on a constructed `Verdict`), which runs natively only. An aggregator-level control runs natively and in the SP1 executor, never on one side only, except a binding control, which only proving can reach (the SP1 executor does not check `verify_sp1_proof`), so it runs on a GPU (`SPEC.md` §2.1 tables).
